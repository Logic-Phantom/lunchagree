# 합의(추천·투표) 규칙

코드: `app/src/domain/*`(순수 TS), 서버 그룹 요약: `get_room_state`(SQL). 상수: `lunch-policy.ts`.

## 1. 그룹 조건 (개인 값 → 그룹 값)
| 항목 | 규칙 | 화면 표기 |
|---|---|---|
| 예산 | 각자 상한의 **최솟값**(정한 사람만) | "그룹 상한 1만원" |
| 걷기 한도 | 각자 한도의 **최솟값** | "걷기 10분 이내" |
| 못 먹는 것 | **합집합** | "해산물 제외" |
| 먹고 싶은 것 | 태그별 원한 사람 수 + 참가자당 합 1로 정규화한 가중치 | "4명 중 3명이 원한 한식" |

누가 무엇을 골랐는지는 표시하지 않는다(공유 방은 서버가 개인 값을 내보내지 않음).

## 2. 하드 조건 (자동 완화 없음)
순서대로 한 가지 이유로만 센다: ① 못 먹는 것(`exclude` 종류) → ② 예산(가격을 아는 후보만) → ③ 걷기 한도(좌표를 아는 후보만).
모르는 값은 막지 않고 "가격 미확인", "거리 미확인"으로 표시한다.
후보가 3개 미만이면 "조건에 맞는 후보가 부족해요" + 막힌 이유별 개수(그룹 수준). 완화는 사용자가 직접(못 먹는 것은 완화 버튼 없음).

## 3. 못 먹는 것 판정
공공데이터에는 메뉴가 없다 → 종류 태그로만.
- `exclude`: 그 종류 대부분이 해당(예: 해산물·날것 → 회·해산물).
- `check`: 해당 메뉴가 있을 수 있음 → "메뉴 확인 필요".
- 종류 미상 후보는 칩이 하나라도 있으면 "메뉴 확인 필요".
- 알레르기 안전을 보증하는 문구는 쓰지 않는다.

## 4. 점수 (화면 비노출)
`score = 0.7 × like + 0.3 × distance`
- `like` = 후보 태그 중 가장 큰 가중치 ÷ 조건 입력 인원 (0~1)
- `distance` = `1 − 도보분 ÷ (걷기한도 ?? 15)`, 좌표 모르면 0
- 도보분 = `ceil(직선거리 × 1.3 ÷ 75)`, 직선거리는 **후보를 넣은 사람의 현재 위치** 기준(좌표는 저장하지 않고 분만 저장), 항상 "(추정)"
- 정렬: 점수 ↓ → 도보분 ↑(모름은 뒤) → 이름 → id (결정적)

## 5. 투표
- 추천 상위 최대 3곳, 1인 1표, 바꾸면 덮어쓰기(서버 `(room_id, participant_id)` PK).
- 최다 득표 1곳 → 결정. **동률은 자동 결정하지 않는다** → 방장이 고르거나 재투표(표 초기화).
- 방장만 투표 시작·마감 가능.
